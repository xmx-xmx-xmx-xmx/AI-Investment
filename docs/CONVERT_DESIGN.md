## 0. 一句话结论

交易流水表目前只能表达「单标的、单方向的一次买卖」。一次**基金转换**（转出 A 份额 → 转入 B 份额）在现有链路上会被**静默记成买入**：转出方份额不扣、转入方凭空增加，底仓直接失真且不报错。改造目标 = 让「转换」成为一等公民，从**录入 → 确认 → 落底仓 → 简报/策略**四段全程可表达。

**实施结果**：后端四段已全部打通；唯一剩余环节是手机端的快捷指令（改完即闭环）。

#### 1.2.1 iOS 快捷指令「理财买入/卖出记账模块」实测结构

来源：`https://www.icloud.com/shortcuts/2e3af95dda97404faef4242092607162`（经 iCloud records API 下载 plist 解析，31 个动作、10456 字节）

**流程**

```
[0] 延迟 2s → [1] 截屏 → [2] extracttextfromimage（iOS 本地 OCR）
   → [3] 把 OCR 原文塞进一段写死的提示词
   → [4] runworkflow → 子快捷指令「Qwen_Core」（把整段文本交给 LLM 返回 JSON）
   → [5] 显示结果
   → [6-21] 按 key 取出 8 个字段 → setvariable
   → [22-24] 交易时间 → 秒级时间戳（1970-01-01 08:00:00 起算）
   → [25-28] POST 换 tenant_access_token
   → [29] POST 建记录 → [30] 通知「✅ 成功记录一笔交易」
```

**写入飞书的字段（8 个，界面上就是这些列名）**

| 写入列 | 来源 |
|--------|------|
| 交易单号 | JSON `order_id` |
| 产品名称 | JSON `product_name` |
| 交易金额 | JSON `amount` |
| 交易时间 | JSON `trade_time` → 秒级时间戳 |
| 买卖方向 | JSON `action` |
| 状态 | JSON `status` |
| **确认份额** | JSON **`shares`** |
| **确认净值** | JSON **`nav`** |

> 写入端点：`POST /bitable/v1/apps/RrbywOLz3iYfZAkiZyfc3kh6nKg/tables/tblbnD3uaEdohjji/records`
> （该 app_token 与 `.env` 的 `FEISHU_BITABLE_TOKEN` 字符串不同，但实测**指向同一个表** `AI投资数据库`，非问题。）

**⚠️ 提示词里的 action 规则正是 bug 源头（原文）**

```
5. "action" (字符串):
    - 如果文本包含"买入金额"或"买入成功"或"份额待确认"，输出 "buy"
    - 如果文本包含"卖出金额"或"卖出份额"或"卖出时间"，输出 "sell"
```

转换单里**既不出现"买入"也不出现"卖出"**（页面写的是"转换"）→ 规则全部落空 → 落到 `buy`。
**这解释了实测那行为什么是 `buy`。**

**其他实测偏差（同一行佐证）**

| 字段 | 实际写入 | 应有 | 原因 |
|------|----------|------|------|
| 买卖方向 | `buy` | `convert` | 上述规则落空 |
| 交易金额 | `1000` | 无（转换单无金额） | 提示词强制要求 `amount`，LLM 只能编 |
| 交易单号 | `20260917124214` | 30 位真实单号 | 恰是 `交易时间` 去掉分隔符 → LLM 拿日期当单号 |
| 确认份额 | `30` | pending 时应为 null | 提取了截图里的"申请转出份额 30.00" |

**✅ 好消息：录入侧本来就支持"份额"**——提示词第 7 条已提取 `shares` 并写入 `确认份额`。
所以「份额驱动」在录入端**已经具备**，缺的只是把它放到正确的字段语义上。

**✅ 子快捷指令 `Qwen_Core` 已完整解析（2026-09-17）：它只做"转发 + 取字段"，无任何 schema 约束。**

全文 5 个动作，链路极简：

```
[0] 注释（API 配置说明）
[1] URL → https://api.siliconflow.cn/v1/chat/completions
[2] POST（头部 Content-Type / Authorization: Bearer <key>）
      请求体 { "model": "Qwen/Qwen3-30B-A3B-Instruct-2507",
               "messages": [ {"role":"user", "content": <主快捷指令传入的整段文本>} ] }
[3] 获取字典值：choices.1.message.content
[4] 输出（把上面取到的字符串回传给主快捷指令）
```

关键结论（可直接据此免改）：

| 观察 | 含义 |
|------|------|
| `content` = `ExtensionInput`（整段入参原样塞进**单个 user 消息**） | 提示词、字段定义、few-shot **全部由主快捷指令的动作 [3] 提供**，这里不追加任何 system 约束 |
| 没有 `response_format` / `tools` / schema 参数 | **不会吃掉新增字段**。加 `target_product` / `transfer_shares` **无需改动 Qwen_Core** |
| 取的是 `choices.1.message.content`（索引是 **1**） | ⚠️ 看似"应是 0"，但**实测可用**（现有记录就是这么产生的）——Shortcuts 点号路径取数组是 **1-based**。**千万别改成 0** |
| 独立 API Key（与项目 `.env` 的 `SILICONFLOW_API_KEY` **不同**，两者配额各自独立） | 手机记账的调用**不消耗**项目 GitHub Actions 的配额；反之项目被限流也不影响手机端 |
| 模型 `Qwen/Qwen3-30B-A3B-Instruct-2507` | 与项目主模型（DeepSeek-V3.2）不同，互不影响 |

> ⚠️ **安全**：该 Key 以明文写在动作 [2] 的 Authorization 头部里。任何人拿到这份 `.shortcut` 文件或 iCloud 分享链接即可读取。若曾把链接给过他人，建议去 SiliconFlow 控制台轮换该 Key（只需改动作 [2] 一处）。

## 2. 设计决策（需要你拍板）

| # | 决策点 | 选项 | 建议 |
|---|--------|------|------|
| **D1** | 转换在表里怎么表达 | (a) **一行 `convert` + `转入标的` 列**<br>(b) 拆两行 `sell` + `buy` | **(a)**。语义完整、一次申请一行、与订单号一一对应，对账方便。(b) 会让"一次申请"变成两行、金额还未知 |
| **D2** | 驱动方式 | (a) **份额优先**：新增输入列 `转出份额`，有则直接用<br>(b) 维持金额驱动 | **(a)**，且保留回退：`有份额用份额，无份额用金额/净值`。买入单仍走金额 |
| **D3** | 转换的"转入"是否计入买入冷却期 | (a) 计入 (b) 不计入 | **(a)**。转换本质是一次调仓买入，计入更符合纪律；且避免"用转换绕过冷却期" |
| **D4** | 转换费 | 截图未显示费用 | 先按**无费**处理（转出金额 = 转入金额）；若真实确认单有费用，再加 `转换费` 列 |
| **D5** | 确认数据从哪来 | (a) 系统按 T 日净值算<br>(b) **用户填优先，缺失则系统算** | **(b)**。9/21 确认单会直接给出转入份额/净值，让用户填最准，还能绕开净值抓取的不确定性 |

### 3.5 iOS 快捷指令「理财买入/卖出记账模块」（**必改，且是全链路的第一环**）

改动集中在 3 个动作，都是"改文字/加字段"，不涉及重写流程：

| 动作 | 现状 | 改成 |
|------|------|------|
| **[3] 提示词** | `action` 只有 buy/sell 两值；字段 8 个 | ① `action` 加第三值：**含"转换"/"基金转换" → `convert`**，并把兜底从"默认 buy"改为**无法判断就输出 `unknown`**（让后端跳过而不是记错）<br>② 新增输出 **`target_product`**（转入基金全名）<br>③ 新增输出 **`transfer_shares`**（申请转出份额）<br>④ 转换单的 `amount` 明确输出 `null`（不要编）<br>⑤ `order_id` 明确"转换单的订单号是 28-32 位长数字"，避免拿日期当单号<br>⑥ 补一条**转换单的 few-shot 示例** |
| **[6-21] 取字段** | 取 8 个 key | 增加 2 组 `getvalueforkey` + `setvariable`：`target_product → 转入标的`、`transfer_shares → 转出份额` |
| **[29] POST body** | 写 8 个字段 | 增加 `转入标的`、`转出份额` 两个 key |

> 转换行的 `确认份额`/`确认净值` 保留为空（pending 时本就应为 null，由后端 `pending_resolver` 回填）。

### 7.1 实施中新增的设计修正（偏离 v1 设计，需知悉）

**D5 加了闸门**：v1 设计是"用户在 `确认份额` 填了值就优先采用"。实施时发现一个漏洞 ——
快捷指令会把 OCR 出的**申请转出份额**写进 `确认份额`（实测那行 `30` 就是这么来的），
若直接采信，会把"转出 200 份"误读成"转入 200 份"，而正确值约 198.20。

**修正**：必须 **`确认份额` 与 `确认净值` 同时填写** 才认作用户显式覆盖
（确认净值是快捷指令写不出的——它只能拿到申请单，拿不到确认单）。
只填 `确认份额` 时走系统折算。已由 `test_convert_shares_alone_is_not_confirmation` 锁住。
